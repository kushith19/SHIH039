# Telemetry Ingestion Service

This service is a separate microservice responsible for receiving, validating, and storing telemetry generated by the Smart City Telemetry Generator.

It acts as both:

1. **Data Ingestion Layer**:
   - receives `CitySnapshot` payloads from the Telemetry Generator
   - validates and stores telemetry

2. **Data Access Layer**:
   - exposes read-only query APIs for downstream intelligence services

It is intentionally decoupled from the generator and does not contain city-specific logic.

### Architecture

```
Telemetry Generator
        |
        | CitySnapshot HTTP Stream
        ↓
Telemetry Ingestion Service
        |
        ├── TimescaleDB Storage
        |
        └── Query APIs
              |
              ↓
       Detection / TGNN / AI Commander / Analytics
```

---

# Architecture Overview

**Telemetry Generator**:
- produces `CitySnapshot`s containing:
  - infrastructure endpoints
  - runtime state
  - behaviour state
  - context/dependency effects
  - numerical telemetry metrics

**Snapshot Forwarder**:
- sends snapshots using:
  ```
  POST /ingest/snapshot
  ```

**Telemetry Ingestion**:
- validates payloads
- extracts telemetry rows
- batch inserts into TimescaleDB

**Query Layer**:
- provides telemetry and infrastructure data to external services without direct database access.

# Database Architecture

The database acts as the historical operational memory of the simulated city.

Telemetry data is stored as time-series data to support:
- recent window analysis
- historical baseline creation
- anomaly detection
- graph intelligence processing

### `infrastructure`
Stores registered city infrastructure endpoints.

**Fields**:
- `id` (VARCHAR(255), Primary Key)
- `name` (VARCHAR(255))
- `type` (VARCHAR(100))
- `sector` (VARCHAR(100), Optional)
- `criticality` (VARCHAR(50), Optional)

### `telemetry`
Stores time-series metric data.

**Fields**:
- `time` (TIMESTAMPTZ)
- `endpoint_id` (VARCHAR(255), Foreign Key -> `infrastructure.id`)
- `metric_name` (VARCHAR(255))
- `value` (DOUBLE PRECISION)
- `unit` (VARCHAR(50))
- `simulation_tick` (BIGINT)

**Key Details**:
- `telemetry` is configured as a TimescaleDB hypertable partitioned by `time`.
- Duplicate telemetry points are prevented using a `UNIQUE(endpoint_id, metric_name, simulation_tick, time)` constraint.
- Indexed for fast historical time-series queries.

# API Reference

## Health Check
`GET /health`

**Purpose**:
Verify service and database connectivity.

## Infrastructure Registration
`POST /ingest/infrastructure`

**Purpose**:
Registers infrastructure metadata before telemetry ingestion.

**Used for**:
- loading the 42 city infrastructure endpoints
- creating database references required by telemetry

## Snapshot Ingestion
`POST /ingest/snapshot`

**Purpose**:
Receives `CitySnapshot` payloads from the Telemetry Generator.

**Flow**:
```
CitySnapshot
↓
Validation
↓
Extraction
↓
Batch Insert
↓
TimescaleDB
```

## Query APIs

### Get Infrastructure
`GET /api/infrastructure`

**Purpose**:
Returns registered infrastructure nodes.

**Used by**:
- graph construction
- TGNN detection
- dependency analysis

**Example response**:
```json
{
  "count": 42,
  "infrastructure": []
}
```

---

### Get Recent Telemetry
`GET /api/telemetry/recent?minutes=5`

**Purpose**:
Returns telemetry from a recent time window.

**Used for**:
- real-time anomaly detection
- live monitoring

---

### Get Endpoint History
`GET /api/telemetry/history/:endpointId?hours=24`

**Purpose**:
Returns historical telemetry for an endpoint.

**Used for**:
- baseline analysis
- behavioural comparison
- trend detection

# Running Locally

### Install Dependencies
```bash
pnpm install
```

### Start Database and Service
```bash
docker compose up -d
```

### Verify Running Containers
```bash
docker compose ps
```

### Verifying the Setup

After starting the service:

1. Register infrastructure:
   ```bash
   POST /ingest/infrastructure
   ```
2. Start telemetry generator.
3. Verify telemetry storage:
   ```bash
   GET /api/telemetry/recent?minutes=5
   ```

# Development Guidelines

This service should remain:
- generic
- schema-driven
- independent from city-specific logic

Do not add:
- detection algorithms
- attack simulation
- AI reasoning
- visualization logic

Those belong to separate services consuming this data.
