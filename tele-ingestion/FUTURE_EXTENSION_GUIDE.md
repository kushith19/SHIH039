# Telemetry Ingestion Service — Future Extension Guide

## 1. Current Architecture

The Telemetry Ingestion microservice serves as the single, generic data boundary between simulation sources (the Telemetry Generator) and downstream processing engines.

```
Telemetry Generator
        |
        | CitySnapshot HTTP POST
        ↓
Telemetry Ingestion Service
        |
        ↓
TimescaleDB
        |
        ↓
Detection / Analytics / AI Services
```

### Decoupling Principles
This service is intentionally generic. To preserve clean system boundaries, it must **never** contain:
- City Model schemas or domain definitions
- Real-time detection algorithms or anomaly scoring logic
- Cyber attack simulations or threat scenarios
- Hardcoded rules specific to individual infrastructure endpoints

---

## 2. Current Database Model

The database setup consists of two primary PostgreSQL/TimescaleDB tables.

### `infrastructure` Table
Stores metadata for registered city infrastructure entities.

- **`id`** (VARCHAR(255), PK): Unique identifier for the endpoint (e.g., `hospital-api-gateway`).
- **`name`** (VARCHAR(255)): Display name of the endpoint.
- **`type`** (VARCHAR(100)): Endpoint classification (e.g., `camera`, `gateway`).
- **`sector`** (VARCHAR(100), Optional): Domain sector (e.g., `healthcare`, `energy`).
- **`criticality`** (VARCHAR(50), Optional): Priority level (e.g., `high`, `critical`).

*Note:* This table holds static entity metadata registered prior to telemetry ingestion.

### `telemetry` Table
Stores time-series metric readings as a TimescaleDB hypertable.

- **`time`** (TIMESTAMPTZ): Timestamp of metric recording.
- **`endpoint_id`** (VARCHAR(255), FK): References `infrastructure(id)`.
- **`metric_name`** (VARCHAR(255)): Name of the metric (e.g., `requests_per_second`).
- **`value`** (DOUBLE PRECISION): Numerical metric reading.
- **`unit`** (VARCHAR(50)): Unit of measurement (e.g., `requests/s`, `ms`).
- **`simulation_tick`** (BIGINT): The generator simulation tick number.

*Note:* New numerical metrics should be ingested as new `metric_name` values in this long-format table, rather than altering table schemas to add new columns.

## 3. Adding Future Telemetry Fields

When extending the data model for new telemetry types, distinguish between **Metrics** and **Metadata**:

### Metrics
Numerical time-series observations (e.g., `CPU usage`, `latency`, `packet rate`, `error rate`).
- **Storage Strategy:** Insert directly into the existing `telemetry` table using standard `metric_name`/`value`/`unit` tuples.

### Metadata
Contextual annotations, operational descriptors, or non-numerical telemetry (e.g., `model version`, `source service`, `confidence score`, `attack identifiers`).
- **Storage Strategy:** Use a `JSONB` column on target domain tables or create dedicated extension tables to keep time-series queries lean and performant.

---

## 4. Future WebSocket Extension

When adding WebSocket transport for real-time streaming, treat WebSockets as an alternative ingress adapter that feeds into the existing core ingestion engine.

```
HTTP Transport     WebSocket Transport
      |                     |
      +----------+----------+
                 |
                 ↓
         Ingestion Service
                 |
             Repository
                 |
                 ↓
            TimescaleDB
```

- **Architecture Rule:** Transports should only parse network transport protocols, delegate validation to shared Zod schemas, and invoke `IngestionService.processSnapshot()`. Do not duplicate business or storage logic in socket event handlers.

## 5. Future Data Domains

As the platform expands, avoid forcing non-telemetry domains into the `telemetry` table. Create distinct domain tables:

### Security Events
- **Purpose:** Capture explicit security alerts, compromises, and malware indicators.
- **Example Fields:** `event_id`, `endpoint_id`, `threat_level`, `signature`, `payload_hash`, `time`.

### Detection Results
- **Purpose:** Store output from TGNN anomaly detection engines and risk evaluation models.
- **Example Fields:** `detection_id`, `node_id`, `anomaly_score`, `risk_level`, `campaign_id`, `time`.

### Recommendations
- **Purpose:** Persist autonomous decisions and mitigation commands generated by the AI Commander.
- **Example Fields:** `recommendation_id`, `target_endpoint_id`, `action_type`, `confidence`, `status`, `time`.

---

## 6. Database Scaling Considerations

For production or long-running digital twin deployments:
- **TimescaleDB Retention Policies:** Configure `drop_chunks()` policies to drop or archive telemetry chunks older than a specified threshold (e.g., 30 days).
- **Continuous Aggregates:** Implement TimescaleDB continuous aggregates for automated 1-minute, 1-hour, or 1-day rollups to accelerate analytical dashboard queries.
- **Read Replicas & Analytics Isolation:** Downstream services (TGNN, AI Commander) should read from read-replicas or Continuous Aggregate views to prevent analytical workloads from impacting ingestion throughput.

---

## 7. Development Rules

### DO:
- Keep the ingestion service strictly generic and domain-agnostic.
- Implement new ingress transports (e.g., WebSockets, gRPC) as decoupled adapters calling the shared `IngestionService`.
- Separate distinct domain concerns (telemetry vs. security events vs. detections) into individual database tables.
- Leverage flexible JSON schemas or normalized row formats for new dynamic fields.

### DO NOT:
- Add detection algorithms, AI models, or threat scoring inside this service.
- Implement attack simulation mechanisms or city-specific business logic here.
- Hardcode city infrastructure endpoints or sector configurations in code.
- Mix heavy analytics, aggregations, or complex reporting queries into the ingestion execution path.
